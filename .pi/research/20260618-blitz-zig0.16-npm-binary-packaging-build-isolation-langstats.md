# Research: Zig 0.16 CLI architecture, npm binary packaging, build isolation, and excluding dev/bench from releases/language stats (Blitz)

## Question
What are current best practices for Blitz: Zig 0.16 CLI design, platform binary packaging in npm, build isolation, and excluding bench/dev assets from package release + GitHub language stats?

## Answer / Recommendation
Blitz already follows most correct patterns; tighten with explicit checks.

1) **Keep `std.process.Init` CLI entrypoint + std.Io.**
- Use `pub fn main(init: std.process.Init) !void` for full app lifecycle (gpa/io/environ/args). It is the recommended 0.16 pattern.
- Use `init.minimal.args` when only CLI arg parsing is needed; use arenas for scoped allocations.
- In build, keep `b.standardTargetOptions/standardOptimizeOption` and `b.createModule`-backed modules.

2) **Use explicit packaging allowlists + per-platform optional distribution packages.**
- Root package `files` acts as allowlist; with it, `.npmignore` is not root precedence.
- Keep wrapper package files minimal and explicit.
- Each platform package should remain one-file payload (`bin/blitz` or `bin/blitz.exe`) plus tiny package metadata.
- Verify what ships via `npm pack --dry-run --json`.

3) **Treat bench/dev as runtime-excluded via current files/gitattributes; add CI assertions.**
- `.gitattributes` overrides language stats (`linguist-vendored/generated/documentation`).
- `bench/**` is already marked `linguist-vendored` in repo. Keep it (or `linguist-generated` if diff suppression preferred) and mirror with package allowlists.
- Add explicit pack checks to fail if any bench/dev file leaks into tarball.

4) **Build isolation + reproducibility: separate axes.**
- Zig builds: isolate target/optimize/config from side effects; use matrix CI for all supported targets.
- Keep runtime/bench/test separate commands; avoid mixing bench fixtures with production package contents.
- Add quick gates: `npm pack --dry-run`, platform-package `npm pack` dry-runs, and `zig build -Dtarget=... -Doptimize=...` smoke/test matrix.

## Builder-Ready Implications

### Concrete action list
1. **Add CI checks**
   - `npm pack --dry-run --json` parse output -> fail on any path matching `(^|/)bench/|(^|/)fixtures/|(^|/)scripts/(?!mcp-smoke\.ts$)`.
   - `npm pack ./packages/blitz-*/ --dry-run --json` verify only `bin/blitz*` + package.json.
   - `zig build -Dtarget=<supported> -Doptimize=<fast/release>` for all supported matrix entries in CI.

2. **Keep/refresh package boundaries**
   - Root package `files` remains explicit; do not broaden.
   - Prefer keeping TS source in root only where needed (`scripts/mcp-smoke.ts` currently shipped—decide and document).
   - Keep platform packages as pure binary consumers of `bin/` only.

3. **Enforce language-stats exclusion**
   - Keep current `.gitattributes` entries.
   - Add comment block header in `.gitattributes` explaining intent for reviewer/automation: `bench` and vendored C/grammar sources excluded from language stats.
   - Optional periodic script: `git check-attr linguist-generated linguist-vendored -- .`.

4. **Maintain build isolation**
   - Keep CLI build/test commands side-effect-free.
   - No install/build hooks that compile toolchain during npm install (avoid unexpected network/toolchain drift).

### Risks / residual
- npm behavior with platform-conditional optional dependencies can vary by manager/version (lockfile metadata interpretation). Keep matrix tests for at least npm latest + previous LTS.
- Any future `.npmignore` addition can silently change release surface; codify pack-surface checks to fail on drift.

### Verification hooks to add (minimal)
- `npm pack --dry-run --json | bunx jq '.[]|.files[].path' | rg '(^|/)bench/|(^|/)fixtures/'` (fail if any match)
- `node -e "const fs=require('node:fs');const g=JSON.parse(fs.readFileSync('package.json','utf8'));console.log(g.files.join('\n'))"` for review snapshots
- `zig build -Dtarget=<target> -Doptimize=ReleaseFast -fsanitize=off` (or baseline optimize matrix)
